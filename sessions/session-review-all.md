## 1일차: OT & 방향 정렬 (3/9)

### 1. 부족한 부분

**1-1. 구체적 활동 설계의 부재**
Block 0 "왜 여기 왔나요?"와 Block 4 "자기소개 & 목표 선언"은 제목만 존재하고, 참가자가 실제로 무엇을 하는지(시간 배분, 진행 형식, 아이스브레이킹 방법)가 전혀 명시되어 있지 않다. OT 세션은 학회의 첫인상을 결정하는 자리인데, 진행자의 즉흥에 의존하면 품질 편차가 크다.

**1-2. "만드는 조직"이라는 정체성의 근거 부족**
"배우는 곳이 아니라 만드는 조직"을 선언하지만, 이것이 구체적으로 어떤 기준(매 세션마다 산출물 제출, 11주 후 최종 프로덕트 완성 등)으로 실현되는지 설명이 없다.

**1-3. 산학 프로젝트에 대한 설명 부재**
Block 3에서 "산학 프로젝트 방향"이 Goals에 명시되어 있으나, 보험 도메인이나 산학 협력 기업에 대한 구체적 소개가 없다. Day 4에서 갑자기 보험 도메인이 등장하면 학회원들이 맥락 없이 받아들이게 된다.

### 2. 보충해야 할 부분

**2-1. 11주 커리큘럼 로드맵 시각 자료**
전체 11개 세션이 어떻게 연결되는지 시각적 로드맵(타임라인, 마일스톤)이 필요하다. 학회원이 각 세션의 위치와 의미를 이해해야 동기부여가 유지된다.

**2-2. 지난 학기 결과물의 성공/실패 분석**
Block 2에서 7개 팀 이름을 나열하지만, 각 팀이 "무엇을 만들었고, 어디까지 갔고, 무엇이 부족했는지"를 구조화하여 공유해야 한다. 실패 사례에서의 교훈이 이번 학기의 실행 기준을 세우는 데 훨씬 유용하다.

**2-3. 사전 환경 설정 안내**
Day 2의 Prerequisites가 "노트북, Node.js 설치, Anthropic API Key"인데, Day 1에서 사전 안내(설치 링크, API Key 발급 방법, 예상 비용)를 전달해야 Day 2에서 세팅 시간을 낭비하지 않는다.

### 3. 틀린 부분

**3-1. DB seed 데이터와 실제 커리큘럼 불일치**
DB의 `prisma/seed.ts`에서 session-day1의 제목은 "AI 기초와 프롬프트 엔지니어링"으로 되어 있고, 실제 Day 1은 "OT & 방향 정렬"로 완전히 다르다. 통일 필요.

### 4. 모호한 부분

**4-1. "결과 중심 문화"의 정의**
"결과"가 코드인지, 서비스인지, 발표인지, GitHub 리포지토리인지 명확하지 않다.

**4-2. "실제 실행 수준"의 기준**
MVP인지, 프로토타입인지, 배포 가능 수준인지 기준이 없다.

**4-3. "기준을 세운 날"의 모호함**
어떤 기준인지 구체적으로 정리되어 있지 않다. 합의된 기준(예: "매주 산출물 제출", "코드는 반드시 GitHub에")이 명시되어야 마무리가 의미를 갖는다.

### 5. 붙이면 좋을 부분

- **학회원 역량 사전 조사** (코딩 경험, 사용해본 AI 도구, 관심 도메인) → 팀 구성/난이도 조정에 활용
- **"보험 AI Agent"라는 최종 목표의 예고편** — 데모 영상이나 목업으로 동기부여
- **커뮤니케이션 채널 확정** — Slack/Discord, GitHub Org, Notion 등 가입 시간 배정

## 2일차: AI를 쓰는 사람이 아니라 설계하는 사람으로 (3/12)

### 1. 부족한 부분

**1-1. Node.js / npm 기초 설명 부족**
비전공자에게 `npm`, `npx`, `package.json`, 터미널 사용법 자체가 장벽. "엔진이다"라는 비유만으로는 설치 과정의 에러(PATH, 버전 충돌)를 해결할 수 없다.

**1-2. API Key 비용 및 관리 안내 부재**
토큰당 과금, 요금 한도 설정, Key 유출 시 위험에 대한 설명이 없다. Key를 GitHub에 push하는 사고를 예방해야 한다.

**1-3. Git 실습의 깊이 부족**
conflict 해결, `.gitignore`, commit message 규칙 등이 빠져 있다. 특히 `.gitignore`는 `.env` 파일 유출 방지를 위해 필수.

**1-4. 트러블슈팅 가이드 부재**
포트 충돌, 의존성 에러, Claude Code 인증 실패 등 흔한 문제에 대한 대처법이 없다.

### 2. 보충해야 할 부분

**2-1. 컨텍스트 엔지니어링 실습 강화**
"랜딩페이지 만들어줘" vs "컨텍스트 포함 버전"의 단순 비교를 넘어, 학회원 각자가 자신의 주제로 4대 요소를 작성하고 결과를 비교하는 구조화된 실습이 필요.

**2-2. Claude Code의 차별점 및 동작 원리**
ChatGPT 웹, Cursor와의 차이(로컬 파일 시스템 접근, 터미널 명령 실행 등) 설명 필요.

**2-3. 과제 평가 기준의 구체화**
"3페이지 이상 웹 제작"이라는 양적 기준과 "사고 과정 중심 평가"라는 질적 기준 사이의 관계 정리, 제출 형식 명시 필요.

### 3. 틀린 부분

**3-1. 프로젝트 구조 예시의 부정확함**
`README.md, src/, components/, assets/` → Next.js App Router 기준으로 맞지 않음. 실제 `create-next-app`이 생성하는 구조(`app/`, `public/`, `src/`)를 보여줘야 한다.

**3-2. "컨텍스트 엔지니어링" 용어 정의 범위 충돌**
Day 2의 4대 요소(역할/목표/상태/제약)는 프롬프트 엔지니어링에 가깝다. Day 4의 Context 4요소(Selection/Compression/Framing/Iteration)와 용어적으로 충돌. Day 2에서 "프롬프트 설계의 4대 요소"로 명명하거나 Day 4와 연결하는 브릿지 필요.

### 4. 모호한 부분

**4-1. "사고 전환"의 구체적 의미** — "채팅으로 질문" → "파일 시스템 위에서 코드 생성"인지, "프롬프트 설계"인지 불명확.

**4-2. "평균적인 결과"의 정의** — LLM이 zero context에서 생성하는 generic 출력을 의미하는 것이라면 실습에서 명시적으로 비교 필요.

**4-3. Next.js 선택 이유** — 최종 프로젝트(보험 Agent)가 Next.js 기반인지, Day 2 실습용인지 불분명. Day 3에서 Python을 사용하므로 두 언어의 관계 정리 필요.

### 5. 붙이면 좋을 부분

- **`.env` + `.gitignore` 설정 실습** — Day 3의 `.env` 관리 사전 준비
- **실습 결과물 라이브 공유 시간** — 2-3명이 프롬프트와 결과를 공유
- **CLAUDE.md 소개** — 프로젝트 맥락 파일로 컨텍스트 엔지니어링의 실전 적용

## 3일차: API & Tool & Agent Loop 설계 (3/16)

### 1. 부족한 부분

**1-1. API 호출의 실제 구조 설명 부족**
HTTP 요청/응답 구조(URL, Headers, Body, Status Code), JSON 데이터 형식, `messages` 배열의 역할(system/user/assistant) 등이 없다.

**1-2. Agent Loop의 종료 조건 설계 부족**
루프의 종료 시점(최대 반복 횟수, 완료 조건, 타임아웃)에 대한 설계 원칙이 빠져 있다. Day 4의 "좋은 Agent vs 나쁜 Agent" 논의의 기반이 약해짐.

**1-3. 에러 핸들링 부재**
API 호출 실패, Tool 실행 실패, JSON 파싱 실패 등에 대한 처리 미언급.

**1-4. 단일 호출 한계의 구체적 시나리오 부족**
어떤 상황에서 단일 호출이 실패하는지 구체적 예시가 있어야 Tool과 Agent Loop의 필요성이 자연스럽게 도출됨.

### 2. 보충해야 할 부분

**2-1. OpenAI API vs Anthropic API 차이점 정리**
Day 2(Claude Code) → Day 3(OpenAI client) 전환의 이유와 인터페이스 차이 설명 필요.

**2-2. Tool Calling JSON Schema 작성법**
`type`, `properties`, `required`, `description` 기본 문법과 description이 LLM의 Tool 선택에 미치는 영향 설명 필요.

**2-3. 보험 도메인 브릿지**
"학회 공지 작성기" 실습 마무리 시 "이 구조가 보험 Agent에도 동일하게 적용된다"는 연결 제공.

### 3. 틀린 부분

**3-1. "GPT를 시스템 안에 통합" 표현의 부정확함**
GPT는 OpenAI 특정 모델명. Day 2에서 Claude를 사용했으므로 "LLM을 시스템 안에 통합"이 기술적으로 정확.

**3-2. Brain-Hands 비유의 한계**
Day 3에서 "LLM=Brain"이라 가르치고 Day 4에서 "LLM은 다음 토큰 예측기"라고 정정하면 혼란. Day 3에서부터 "적절한 맥락을 주면 판단처럼 보이는 출력을 생성한다"는 뉘앙스 유지 필요.

### 4. 모호한 부분

**4-1. "Primitive Agent 구조"의 범위** — Day 4의 "Agent = Context Builder + Loop"와의 관계(하위 집합? 단순화 버전?) 미명시.

**4-2. check_required_fields의 역할** — Tool인지, Agent 내부 로직인지, 별도 함수인지 불분명.

**4-3. "LLM은 설계된 시스템"** — 의도는 "LLM을 설계된 시스템의 구성 요소로 활용하라"이지만 문법적으로 오해 가능.

### 5. 붙이면 좋을 부분

- **API 호출 비용 계산 실습** — input/output 토큰 수와 비용 확인 → Day 9 Trace Log의 사전 준비
- **Tool 정의를 직접 설계하는 미니 실습** — Day 4 Agent 설계 사고로의 브릿지
- **Streaming 응답 소개** — 실제 서비스 구현 시 UX 개선에 활용

## 4일차: AI Agent Advanced: 맥락을 통제하는 설계 (3/19)

### 1. 부족한 부분

**1-1. 나쁜/좋은 Agent 비교가 코드 수준에서 부족**
개념적 이해에 그치지 않도록, 동일 입력에 대해 두 코드를 나란히 실행하고 출력을 비교하는 라이브 데모 필요.

**1-2. Context 4요소 실습 깊이 부족**
각 요소(Selection/Compression/Framing/Iteration)를 독립적으로 조작하는 단계적 실습이 필요. 현재는 일괄 비교에 그침.

**1-3. 보험 도메인 사전 지식 제공 부족**
Block 8에서 "Mortality, Hazard rate, 기존 가정 테이블"이 갑자기 등장. 보험학/계리학 비전공자를 위한 도메인 입문 설명 필요.

**1-4. Evaluation(Block 6)의 구체적 방법론 부재**
"정확도보다 맥락 기반 평가"라는 방향은 좋으나, 실제 평가 메트릭/데이터셋/절차가 없음.

### 2. 보충해야 할 부분

**2-1. Day 2 Context 4대 요소와 Day 4 Context 4요소의 관계 정리**
역할/목표/상태/제약 = 프롬프트 레벨, Selection/Compression/Framing/Iteration = 시스템 레벨. 이 계층 구분을 명시적으로 연결해야 "4요소가 두 개" 혼란 방지.

**2-2. build_context()와 update_context()의 구체적 구현 예시**
특히 update_context()가 Tool 호출 결과, 에러 정보를 어떻게 state에 반영하는지 코드로 보여줘야 Day 3 Agent Loop와 Day 9 KPI Gate 피드백 루프가 연결됨.

**2-3. 산학 프로젝트의 구체적 범위**
Feature Discovery Agent인지, 클레임 처리 Agent인지 범위 명시 필요.

**2-4. 과제 템플릿/루브릭**
"보험 도메인 Agent 설계 문서"의 구체적 양식 제공 필요.

### 3. 틀린 부분

**3-1. Agent의 보편적 정의가 너무 넓음**
"목표 지향적, 자율적, 반복 루프"는 소프트웨어 Agent 전반의 정의. LLM Agent의 고유 특성(환각, 비결정성, 맥락 의존성)을 포함한 정의 필요.

**3-2. "Agent는 맥락의 결과"**
"Agent의 품질 = 맥락 설계의 품질"이 정확한 표현. 현재 표현은 오해 여지 있음.

### 4. 모호한 부분

- **"나쁜 Agent"의 코드 구조** — Tool 없이 단일 호출인지, 구조는 있는데 맥락이 나쁜 것인지 불명확
- **"계리 연결"의 의미** — 비전공자에게 풀어서 설명 필요
- **Block 7 실습 절차** — 어떤 Agent 구조, 어떤 부분 변경, 비교 기준 불명확
- **4요소 프레임워크 혼재** — Day 2의 4대 요소, Block 4의 goal/risk_definition/constraint/evaluation_metric, Block 5의 4요소가 모두 "4요소"로 불리며 관계 미정리

### 5. 붙이면 좋을 부분

- **보험 도메인 미니 강의 (15-20분)** — 비전공자 대상 보험 기본 구조
- **Day 3 Agent를 보험 도메인에 적용하는 라이브 코딩** — 구조는 같고 맥락만 다르다는 증명
- **Agent 설계 캔버스/템플릿** — 목표 정의, 입출력 스키마, Context 설계, Tool 정의, 평가 기준
- **"Hype 제거" 블록에 구체적 사례** — 단순 RAG 챗봇을 "Agent"로 포장하는 사례 등

## 5일차: 보험 도메인 해체 & 온톨로지 설계 (3/23)

### 1. 부족한 부분

**1-1. 온톨로지 "설계" 실습이 없다**
세션 제목에 "온톨로지 설계"가 포함되어 있지만, 학생들이 직접 온톨로지를 설계해보는 실습 블록이 존재하지 않음. 이론 설명 후 팀별로 자기 보험 도메인에 맞는 온톨로지를 작성하는 워크숍 시간 필요. 6일차에서 ontology.json을 사용하게 되는데, 5일차에서 직접 만들어보지 않으면 6일차에서 기계적으로 따르게 됨.

**1-2. 보험 상품 유형별 차이 설명 부재**
생명보험/손해보험/건강보험/자동차보험 등 상품군에 따라 세그먼트, Hazard 구조, Premium 계산 방식이 다름. 팀 프로젝트에서 각 팀의 타겟 상품에 따라 도메인 지식이 달라지므로 주요 상품군별 차이 개요 필요.

**1-3. 데이터 소스 논의 없음**
Agent가 활용할 데이터 소스(공개 데이터셋, 보험사 내부 데이터 구조, 외부 API)에 대한 구체적 안내 부재.

### 2. 보충해야 할 부분

**2-1. Cox Model 설명의 맥락화**
수식 자체는 정확하나, 왜 보험에서 중요한지, 기존 회귀 모델과의 차이, Agent 설계와의 관계에 대한 직관적 해설 보충 필요.

**2-2. 온톨로지 4계층 간 연결 로직**
계층 간 전이 방식(어떤 규칙으로 Feature→Risk Concept 매핑, 자동화 가능 부분) 구체화 필요. 9일차 Context Builder, Tool Layer에서 직접 사용됨.

**2-3. 구체적 규제 사례**
한국 보험 규제 환경(금감원, 보험업법), EU AI Act의 고위험 AI 분류 등 구체적 사례 필요.

### 3. 틀린 부분

**3-1. Premium 공식의 과도한 단순화**
`Premium = E[Loss|Segment] + Expense + Margin`은 순보험료 기반의 극도로 단순화된 표현. 시간가치 할인, 재보험 비용, 대재해 적립금 등이 빠져 있음. "단순화된 개념 모형"이라는 단서 필요.

**3-2. "개인화 = 리스크 풀 붕괴" 진술이 무조건적**
극단적 개인화의 경우에만 해당. 적절한 개인화는 오히려 역선택을 줄이고 리스크 풀을 안정화할 수 있음. "과도한 개인화"로 조건부 수정 필요.

### 4. 모호한 부분

- **"F→?" 표기** — F가 Feature를 의미하는 것으로 추정되지만 명시적 정의 없음
- **Agent 개입 지점 범위** — Feature Discovery / Actuarial Interpretation Agent 둘 다 만들어야 하는지, 하나만 선택인지 불분명
- **"정보 이득량"** — Information Gain인지, Mutual Information인지, 보험 특화 지표인지 정의 없음

### 5. 붙이면 좋을 부분

- **실제 보험 온톨로지 사례** — ACORD 데이터 표준, NAIC 분류 체계 간략 소개
- **"6일차 Agent 구현을 위한 준비물"** — "팀별 보험 온톨로지 JSON 초안 작성해 오세요" 같은 과제
- **한국 보험시장 특수성** — 실손보험, 보험사기 규모, 디지털 전환 현황 등 현실감 제공

## 6일차: Basic Agent Building Workshop (3/26)

### 1. 부족한 부분

**1-1. 실습 코드 구체성 부족**
파일 구조(agent.py, tools.py 등)와 Checkpoint를 제시하지만, skeleton의 구체적 코드 스니펫이 세션 자료에 포함되어 있는지 불분명. 각 Checkpoint별 starter code 필요.

**1-2. LLM API 선택과 설정 안내 없음**
어떤 LLM을 사용하는지(OpenAI, Claude, 로컬 모델), API 키 관리, 비용 고려사항 미언급.

**1-3. 에러 처리와 디버깅 전략 부족**
실패 원인을 나열하지만, 디버깅 방법론과 로그 전략이 구체적이지 않음.

**1-4. 보험 도메인과의 연결이 약함**
5일차의 온톨로지가 Agent의 Tool이나 Context에 어떻게 통합되는지 구체적 안내 부재. ontology.json이 파일 목록에 있지만 5일차 온톨로지와의 연결 불분명.

### 2. 보충해야 할 부분

**2-1. ReAct 패턴의 보험 맥락 예시**
보험 맥락에서의 step-by-step 시퀀스 필요. 예: "사용자가 '30대 남성 흡연자 보험료 산정' 요청 → Agent Reason → ontology_lookup 호출 → hazard_multiplier 반환 → 다음 단계..."

**2-2. Checkpoint 간 난이도 격차 보완**
CP1→CP2, CP4→CP5 전환이 크다. 힌트나 중간 단계, "참고 구현" 단계별 제공 필요.

**2-3. Stop Condition 다양화**
max_steps 외에 목표 달성, 타임아웃, 비용 한도, 반복 감지 등 다양한 종료 조건 소개 필요. 7일차 평가, 9일차 KPI Gate로의 확장 기반.

### 3. 틀린 부분

**3-1. 프레임워크 레퍼런스 버전 문제**
OpenAI Agents SDK, AutoGen 등은 API가 빠르게 변경됨. 특정 버전 명시 또는 "참고용이며 직접 사용하지 않음" 명확화 필요.

**3-2. A~F 6단계의 한정 필요**
6단계를 "전형적 구조"로 제시하지만, Planning, Memory, Multi-Agent 등이 빠져 있음. "가장 기본적인 Single-Agent Loop이며, 더 복잡한 구조가 존재한다"는 한정 문구 필요. 9일차에서 9블록으로 확장됨.

### 4. 모호한 부분

- **"Checkpoint 방식" 실습의 시간 배분/진행 방식** — 세션 내 전부 완료인지, 일부 과제인지, 팀/개인 단위인지 불분명
- **state.json의 스키마** — 어떤 필드를 갖는지, 루프에서 어떻게 읽고 쓰는지 미설명
- **run_report.md의 용도와 형식** — 어떤 내용을 담는지 정의 없음

### 5. 붙이면 좋을 부분

- **세션 시작 시 "작동하는 최소 Agent" 데모** — 5분 이내, 목표 이미지 제공
- **Tool 정의를 JSON Schema 기반으로 보여주기** — LLM API의 Tool 스키마 작성 방법
- **페어 프로그래밍 방식 실습** — 2인 1조로 완주율 향상

## 7일차: Agent 성공 기준 정의 & 보험 도메인 적용 (3/30)

### 1. 부족한 부분

**1-1. 테스트 케이스 설계 방법론 부재**
좋은 테스트 케이스를 어떻게 설계하는지(edge case 식별, 대표성, positive/negative 균형, 보험 특화 시나리오)에 대한 가이드 필요. 9일차에서 15개 이상을 요구하는데 질을 높이는 방법을 가르쳐야 함.

**1-2. Baseline 비교 대상 없음**
KPI 점수가 "좋은지 나쁜지" 판단할 기준이 없음. 규칙 기반 baseline이나 단순 LLM 호출 baseline과 비교해야 Agent의 가치를 증명할 수 있음.

**1-3. 보험 특화 KPI 6개의 코드 구현 예시 부족**
각 KPI의 scorer 로직 예시가 필요. 함수 시그니처, 입출력, threshold 등.

### 2. 보충해야 할 부분

**2-1. 보편 7대 축과 보험 KPI 6개 간의 관계 매핑**
예: "Actuarial Linkability는 Task Success의 보험 특화 하위 지표". 9일차 KPI Gate의 Hard/Soft/Escalation 분류 판단의 전제.

**2-2. "보험 KPI 60%+"의 의미 명확화**
가중치 배분인지 점수 기준인지 불명확. 근거 설명 필요.

**2-3. Report Generator 구체적 포맷**
리포트의 섹션, 형식(Markdown/HTML/PDF) 구체화 필요. 9일차 "하이브리드 구조" 요구사항과 연결.

### 3. 틀린 부분

**3-1. "성공 기준 = 측정 코드"는 과도한 단순화**
Explainability는 인간 평가 필요, Business Impact는 배포 후 측정 가능. "자동 측정 가능한 것은 코드로, 그렇지 않은 것은 평가 프로토콜로"가 정확.

**3-2. Test Set 10개는 통계적으로 부족**
한 개 오류 = 10%p 변동. 최소 30개 권장, "10개는 시작점이며 충분하지 않다" 명시 필요.

### 4. 모호한 부분

- **"Hazard Reasonableness"** — 정답 레이블 기반(supervised)인지, 전문가 리뷰(human eval)인지, 내적 일관성(self-consistency)인지에 따라 구현이 달라짐
- **"Segment Refinement Quality"** — 분산 감소? 손해율 개선? 구체적 metric 없이 "Quality"만으로는 구현 불가
- **"운영진 skeleton"의 제공 범위** — scorer 함수 시그니처만인지, 테스트 프레임워크까지인지, 어떤 언어인지에 따라 난이도가 크게 달라짐

### 5. 붙이면 좋을 부분

- **Agent 평가 학술적 배경** — AgentBench, SWE-bench, GAIA 등 벤치마크 간략 소개
- **KPI 시각화 대시보드/리더보드** — 팀 간 비교로 동기부여
- **A/B 테스트 · Ablation Study 개념** — Tool/온톨로지를 빼면 점수가 얼마나 떨어지는가 → 최종 발표 "한계" 섹션에 활용
- **과제 제출 형식/평가 루브릭** — 분량, 형식, 필수 항목, 평가 기준 명시

## 9일차: 보험 Agent 시스템 통합 설계 워크샵 (4/6)

### 1. 부족한 부분

**1-1. Multi-Agent 아키텍처 논의 없음**
9블록은 Single-Agent 전제. 5일차에서 Feature Discovery + Actuarial Interpretation 두 Agent를 제시했으므로, 복수 Agent 통합/조율(Orchestrator, Sequential Chain, 병렬 실행)에 대한 가이드 필요.

**1-2. 비용 관리(Cost Management) 부족**
Trace Log에 "비용" 필드를 포함하지만, Token 사용량 모니터링, 비용 상한 설정, 캐싱 전략 등의 구체적 내용이 없음. 학생 프로젝트에서 API 비용은 실질적 제약.

**1-3. 테스트 전략이 구조적으로 부족**
"test_cases 15개"에 그치지 않고, 단위 테스트(Tool 개별), 통합 테스트(9블록 e2e), 회귀 테스트(온톨로지 변경 시) 등 테스트 계층 가이드 필요.

### 2. 보충해야 할 부분

**2-1. Block 0과 Block 1의 중복 정리**
둘 다 보험 AI 실패 유형 3가지와 "작동 ≠ 도입"을 설명. Block 0은 배경 동기 축약, Block 1은 중간발표 기반 구체적 문제점 분석에 집중하도록 분리 필요.

**2-2. Guardrails 구현의 구체적 방법**
키워드 필터인지, 분류 모델인지, 기존 라이브러리(Guardrails AI, NeMo Guardrails)인지 구체화 필요. 또한 Injection 방어가 Should가 아니라 Must여야 하지 않는가?

**2-3. 온톨로지 Semantic Versioning 실제 적용 예시**
보험 맥락 실례 필요. 예: "새 risk concept 'cyber_risk' 추가 = MINOR", "'smoking_status'→'tobacco_use' 이름 변경 = MAJOR"

**2-4. Escalation 설계 구체화**
누구에게, 어떤 형식으로, 어떤 정보를 포함하여 에스컬레이션하는지. 학생 프로젝트에서의 시뮬레이션 방법(콘솔 로그+대기, mock approval) 제시 필요.

### 3. 틀린 부분

**3-1. "수치 = 템플릿(환각 위험 0%)" 부정확**
템플릿에 삽입되는 수치가 이전 단계(LLM 판단, Tool 결과)에서 온 것이면 정확성은 이전 단계에 의존. "LLM의 수치 생성 환각을 방지한다"로 수정 필요.

**3-2. mapping_presence_rate의 Gate 분류 재고**
Soft Gate(재시도)로 분류되어 있으나, 매핑이 완전 누락된 출력을 허용하는 것은 위험. 최소 매핑율(0.8)을 Hard Gate로, 완전 매핑(1.0)을 Soft Gate로 이중 설계가 적절.

### 4. 모호한 부분

- **9블록이 물리적 모듈인지 논리적 단계인지** — 9개 파일/서비스로 구현해야 하는지, 하나의 스크립트 안 9개 함수인지 불분명. 학생 프로젝트 규모에 맞는 구현 수준 가이드 필요.
- **Must/Should/Could 분류 기준** — 왜 특정 항목이 Must이고 다른 것이 Should인지 근거 없음. "Injection 방어"가 Should인 이유?
- **"Circuit breaker"의 보험 맥락 적용** — 구체적 시나리오와 규칙 기반 fallback 형태 예시 없음
- **최종 발표 평가 기준(루브릭)** — 5가지 산출물의 구체적 채점 기준 없음

### 5. 붙이면 좋을 부분

- **실제 보험사/인슈어테크 AI 도입 사례** — Lemonade, Tractable, Shift Technology, KB손해보험, 삼성화재 등
- **장애 대응 시나리오(FMEA)** — 각 블록 실패 시 시스템 영향 분석
- **After Action Review 템플릿** — 팀별 자기 설계의 강점/약점/리스크 자가 평가
- **Observability 개념 소개** — Logging + Metrics + Tracing (OpenTelemetry 참조)
- **팀 간 아키텍처 리뷰 시간** — 10~15분, 상호 설계 피드백

## 전체 커리큘럼 흐름 관점의 구조적 이슈

### 1. 용어 프레임워크의 충돌
- Day 2: "Context 4대 요소" (역할/목표/상태/제약) — 프롬프트 레벨
- Day 4 Block 4: goal/risk_definition/constraint/evaluation_metric — 도메인 레벨
- Day 4 Block 5: "Context 4요소" (Selection/Compression/Framing/Iteration) — 시스템 레벨

모두 "4요소"로 불리며 서로 다른 레벨의 개념. 통합 메타 프레임워크 또는 명확한 계층 구분 필요.

### 2. 프로그래밍 언어 전환 문제
Day 2는 JavaScript/TypeScript(Node.js, Next.js), Day 3 이후는 Python(OpenAI client). 전환의 이유와 학회원이 어디에 집중해야 하는지 정리 필요.

### 3. 보험 도메인 도입 시점이 늦음
Day 1-3에서 보험 언급이 전혀 없다가 Day 4 후반에서 갑자기 등장. Day 1에서 방향 예고, Day 2-3 실습에 보험 시나리오를 일부 섞으면 전환이 자연스러워짐.

### 4. Day 4의 과밀도
